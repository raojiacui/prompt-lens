## 如何使用这份清单

本清单固定为 A01-A15，共 15 个整改主题。其中部分是之前六项问题的进一步定位，并非全部为新问题。每项只依据可定位的代码行为，不把偏好的目录结构、框架替换或未发生的容量需求列为缺陷。

P1 表示对应接口对外开放前应处理的权限、扣费、数据或主要功能问题；P2 表示对应功能上线时应处理的可靠性问题。若某功能不在本次上线范围，可在服务端关闭入口后延期，而不是只隐藏按钮。

## A01 / P1：上传记录与分析入口的状态契约不一致

- 证据：`app/api/upload/complete/route.ts:35` 写入 `phase: completed`；`lib/billing/commercial-media.ts:11` 只接受 `presigned/server-upload`。`app/api/upload/route.ts` 已不再写 presigned 日志。
- 触发：通过当前 R2 直传流程完成一个新文件，再提交普通或商业分析。
- 影响：文件真实存在且归用户所有，也会被拒绝为 `UPLOAD_NOT_OWNED`。链接导入仍写 server-upload，因此可能出现链接可用、本地上传不可用的差异。
- 处理：定义唯一的已验证上传状态；统一普通上传、素材上传、链接导入与归属查询。签发 URL 不能等价于上传完成。
- 验收：从真实上传完成处理函数写出的数据库记录进入实际归属校验；别人的记录、仅获签名但未上传的对象必须拒绝。

## A02 / P1：Agent 生成工具绕过平台 Key 使用规则

- 证据：`lib/agent/tools/call-existing-video-generate-api.ts:51` 直接使用 `userKey || 平台环境变量`；工具仍注册于 `lib/agent/tools/index.ts`，AI planner 可选用。它没有调用商业报价、试用或管理员授权服务。
- 触发：执行到该工具时用户没有自己的 Key，例如任务规划后用户删除 Key。
- 影响：工具可使用平台 Key 发起真实视频生成，缺少对应平台额度预留和结算；同时只保存 Agent artifact，没有写 `videoGeneration`，给出的任务查询地址可能查不到记录。
- 处理：工具必须调用统一生成服务，明确 BYOK、管理员和已确认平台报价的权限；缺少授权就停止。先保存内部任务，再调用供应商，并把供应商任务关联回内部任务。
- 验收：普通无 Key 用户不能生成；删除 Key 不能自动改由平台支付；创建成功的任务能查询且关联正确用户。

## A03 / P1：Remix 来源版本未验证项目归属

- 证据：`lib/workflow/service.ts:276` 仅按客户端传入的 `sourceVersionId` 查询镜头。路由只验证目标项目属于当前用户。
- 触发：持有自己的项目，同时传入其他项目的版本 ID；跨用户攻击还需要知道对方版本 ID。
- 影响：会读取其他项目的镜头内容并送入模型，创建跨项目的版本及镜头关联。
- 处理：查询来源版本时同时限定项目；数据库关系和服务层共同保证版本、镜头、项目一致。
- 验收：同用户其他项目和其他用户的版本 ID 都不能作为当前项目的来源；拒绝应发生在模型调用之前。

## A04 / P1：媒体地址与对象归属缺少统一校验

- 证据：`app/api/audio-clip/route.ts:63` 根据 URL 提取 Key 后直接使用服务端权限读取 R2，未核对所有者；第 70 行对非 R2 地址直接 fetch。`app/api/workflow/projects/[id]/edit/route.ts` 接受客户端覆盖 sourceVideoUrl，并会签名 R2 地址或进入本地下载。
- 触发：已登录用户提供不属于自己的 R2 对象地址，或提供服务器可访问的非公开网络地址。具体内网可达范围取决于部署网络。
- 影响：存在跨用户对象读取和服务端请求任意地址的风险；是否能利用某个地址不能仅由 URL 格式判断。
- 处理：业务接口接收已验证的媒体 ID；读取和签名之前校验用户归属。外部导入统一走受控入口，限制目的地址、重定向和下载体积。
- 验收：其他用户对象、回环/私网地址及重定向到受限地址都被拒绝，且不会发出下载请求。

## A05 / P1：创作 Agent 的执行与存储仍依赖单进程

- 证据：`lib/agent/runtime.ts:16` 使用内存 Set/Map 记录运行与取消状态，后台执行为裸 Promise；`lib/agent/service.ts:122` 同步入口没有分布式领取；`lib/agent/storage.ts:722` 数据库首次探测失败会回退到 JSON 文件，且结果缓存在进程中。
- 触发：部署多个实例、重复执行请求、实例重启、数据库短暂不可用，或在另一个实例发起取消。
- 影响：可能重复执行外部调用、取消无效、后台任务中断；JSON 回退在临时或只读文件系统上会丢失数据或失败，本地开发固定用 JSON 也会掩盖数据库差异。
- 处理：生产使用数据库唯一事实来源；执行采用原子领取与租约，取消标记持久化，任务由可恢复执行器推进。测试用内存实现可以保留，生产不自动换存储。
- 验收：两个执行器争抢同一任务只执行一次；跨实例取消有效；数据库不可用明确失败，不写入替代文件；重启后状态可解释、可恢复。

## A06 / P1：结果保存、任务进度与恢复结算存在事务间隙

- 证据一：`lib/billing/commercial-analysis.ts:83` 调用 retrySceneAnalysis 保存镜头，随后第 85 行单独保存任务成功计数；`lib/workflow/service.ts:437` 起的重试实现又分开更新镜头与 job。
- 影响一：镜头保存后进程退出，会有已交付结果却未计入结算，后续重试可能因镜头已变化而失败。
- 证据二：`lib/workflow/analysis-tasks.ts:199` 读取过期任务快照后调用结算；结算虽然锁行，但没有重新核对领取时的更新时间/租约，也沿用传入快照。部分后续写入仅按 task id 更新。
- 影响二：执行器延迟返回与恢复器竞争时，旧快照可能覆盖新进度；过期执行器也可能把终态改回 queued。
- 处理：结果、镜头状态、任务 checkpoint 同事务提交；结算读取锁内最新状态；所有写入带领取令牌或版本条件，终态不可逆。
- 验收：在结果写入和 checkpoint 之间注入故障；让恢复器与迟到执行器竞争；最终结果、收费和退款一致，且只有一个终态。

## A07 / P1：部分任务只有提交，没有完整终态处理

- 证据一：`lib/billing/commercial-analysis.ts:39` 先创建 running 的 analysis_preview，探测失败没有失败处理；现有恢复器不覆盖 preview。`lib/workflow/service.ts:253` 会因该 pending 任务阻止删除项目。
- 证据二：项目 audio/edit 路由创建 `GENERATE_AUDIO/RENDER_VIDEO` workflowJobs，但仓库中没有对应完整的后台查询/回调闭环；generation-jobs 查询以 `videoGeneration` 记录为入口，这两处没有创建该记录。
- 证据三：普通分析写入 24 小时 expiresAt，却未据此处理长期 queued 状态。商业任务的 ID 也没有像普通分析那样写入项目 metadata，重新打开项目的轮询路径不统一。
- 处理：为每种开放任务定义领取、成功、失败、未知、超时及查询入口；预处理失败立即终结；恢复与用户重开页面覆盖所有类型。
- 验收：探测失败后可以重试或删除；音频/编辑完成后落库并可展示；关闭浏览器后任务仍能到终态；过期排队任务不会永久占用额度。

## A08 / P1（以仓库 Worker 为准）：剪辑客户端与 Worker 接口不一致

- 证据：`app/api/video-edit/route.ts:135` 调用 /edit 或 /concat；项目 edit 路由也调用 /edit；`workers/ffmpeg-worker/server.mjs:502` 的服务只注册 /healthz、/ingest-media、/breakdown、/commercial-media。
- 另一个部署问题：`app/api/audio-clip/route.ts:12` 硬编码 Windows 的 ffmpeg.exe 路径，并在 Web 进程处理视频。项目 edit 在没有 Worker 配置时回退本地 FFmpeg。
- 影响：若线上部署的是仓库 Worker，标准剪辑请求得到 404；Windows 专用入口在 Linux 运行环境不成立。缺少配置还会改变执行位置和资源要求。
- 处理：选定唯一媒体执行位置，补齐实际需要的 Worker 接口或关闭未实现入口，删除不适用的生产本地回退。
- 验收：在与线上一致的 Linux Worker 上验证剪辑/拼接输出；启动时检查必要接口，而不是等用户提交后才发现缺失。
- 待确认：线上 Worker 是否来自另一套未入库的实现。若是，应先同步契约，不能直接断言线上一定 404。

## A09 / P2：上传体积与资源限制没有贯穿实际数据路径

- 证据：主上传签发时只检查客户端 size；`lib/cloudflare/r2.ts:164` 的签名不绑定申请体积；完成接口只比对客户端新报的 size 与对象大小。`app/api/project-assets/route.ts:40` 仍是整文件 arrayBuffer 上传，无该入口的大小/频率约束。
- Agent 附件仍把 dataUrl/frames 放入 JSON，`lib/agent/service.ts:23` 的限制基于客户端 size，没有限制实际字符串总量、附件数量和帧总量。
- 视频上传允许 500MB，分析 Worker 接受上限是 100MB；用户可能完整上传后才被拒绝。
- 处理：统一每种用途的实际大小限制、完成校验与失败清理；素材和 Agent 附件使用 R2 媒体引用；Worker 设置并发上限和子进程执行期限。
- 验收：谎报体积无效；超限对象拒绝并清理；大文件不经 Web 内存中转；支持范围在上传前后保持一致。

## A10 / P1（商业功能开放时）：新旧钱包与功能授权未统一

- 证据：v6 购买写 commercialWallets/commercialLots；`lib/billing/platform-access.ts:22` 只按旧 creditLedger 的 packageId 判断付费权限；`lib/billing/video-analysis.ts:119` 用该结果决定 trial/platform_credits。`lib/workflow/analysis-routing.ts` 对图片始终不走商业报价。
- 触发：只购买 v6 套餐、没有 BYOK、已用完试用的用户提交图片分析或走旧授权入口。
- 影响：账户有新钱包余额，入口仍按试用处理并拒绝；不同入口展示与使用的余额不同。这不表示商业视频报价路径全部失效。
- 处理：先确定 V2 对外的唯一钱包与功能矩阵；旧余额若需保留，提供明确迁移/兼容策略，不由多个入口自行决定支付来源。
- 验收：同一账户在图片、短视频、拆镜、Agent 和改写入口得到一致且符合产品规则的权限；所有平台付费调用能追溯到同一类账本。

## A11 / P2：仍有长请求与缺少重复提交保护的外部调用

- 证据：`lib/workflow/service.ts:289` 起的 Remix 在一个请求中串行调用模型并逐项写入；音频分析在请求中等待供应商结果；video-generate 与 generation-jobs 在供应商创建后才插入本地记录，没有客户端请求幂等标识。
- 影响：请求超时可能留下半成品；供应商已接受但本地记录/响应丢失后，用户重试可能再次生成并消耗自己的 Key 额度。BYOK 也需要防重复。
- 处理：在同一个任务执行基础上补齐持久化提交和幂等请求；供应商状态未知时显式保留待核对状态。不要用盲目重试弥补未知提交。
- 验收：响应丢失后重复请求返回同一个内部任务；多镜头 Remix 中途退出后可继续或明确失败；不会静默新建另一组付费调用。

## A12 / P2：演示搜索仍在正式 Agent 工具链中

- 证据：`lib/agent/tools/index.ts` 注册 webSearchMockTool；`lib/agent/tools/web-search-mock.ts` 使用固定样例搜索；planner 的多个模板会选它，报告工具继续消费这些结果。
- 影响：研究结果包含样例来源/趋势而非实时检索。数据中带 mock note，不应把它说成完全没有标记，但当前流程仍把它当作成功研究步骤。
- 处理：讨论是否保留联网研究。若本期不接真实来源，关闭该能力或明确为演示；生产模型失败不输出伪装成真实研究的样例结果。测试替身可以保留在测试目录。
- 验收：正式研究输出中的来源可追溯；禁用搜索时明确说明不可用，不生成替代事实。

## A13 / P1（退款开放时）：退款进入 review 后缺少完成核对入口

- 证据：`lib/payments/commercial-refunds.ts:35` 只在当次请求里查询一次支付宝退款；异常转 review，重复请求直接返回已有退款。定时器只处理支付订单/任务，管理员接口列出退款但没有退款查询和最终处置操作。
- 触发：退款已提交，但响应超时或查询暂未确认。
- 影响：退款批次停在 refunding/review，用户额度持续冻结或扣留；真实退款已完成也不一定同步。不能把未知状态直接当失败退还额度。
- 处理：持久化退款核对任务，按同一退款请求号查询；提供基于证据的管理员处置和审计记录。
- 验收：模拟提交响应丢失、查询迟到和重复通知；最终钱款状态、套餐状态及额度一致，不重复退款或解冻。

## A14 / P2：媒体对象缺少完整生命周期

- 证据一：`lib/workflow/service.ts:211` 收集项目引用的对象；删除项目后直接删除所有源对象，没有检查其他项目引用同一上传。当前分析允许同一已拥有上传用于不同项目。
- 影响一：删除项目 A 可能破坏仍引用同一源文件的项目 B；R2 删除失败只有日志，没有持久化清理任务。
- 证据二：商业与 BYOK 生成完成后直接保存供应商 videoUrl，没有转存 R2 的步骤。
- 影响二：“存储都走 R2”尚未覆盖生成结果。外链是否过期取决于供应商，代码无法保证长期可用。
- 处理：媒体对象登记所有者和引用关系；无引用时排队清理并重试；根据产品保留承诺将交付结果归档到 R2。
- 验收：共享源文件删除一个项目后仍可使用；清理失败可重试；若承诺长期保存，供应商链接失效后仍能从 R2 播放。

## A15 / P2（发布前门槛）：迁移与跨模块验收没有统一发布检查

- 证据：代码已经依赖 0017/0018，但 `lib/billing/commercial-readiness.ts:15` 仍只要求人为标记 0015；仓库没有 .github 工作流，package.json 没有串联迁移验证、契约测试和发布检查的脚本。外部 CI 是否存在未核验。
- 测试缺口：`tests/analysis-tasks.test.ts:17` 与 commercial-wallet 测试模拟了上传归属函数；浏览器测试拦截全部 API。因此上一轮 235 个单测与 6 个页面测试通过，也无法发现 A01。
- 处理：先补真实服务层之间的数据库集成测试、Worker 契约测试和部署迁移检查，再做少量真实服务验收。不要以增加模拟测试数量替代关键链路证据。
- 验收：缺少 0017/0018 时发布检查失败；实际上传完成记录可进入分析；跨用户资源被拒绝；故障注入后的结算一致；Linux Worker 的开放接口有验收记录。

## 已有设计中可继续保留的部分

- 主要业务路由已进行登录校验，项目查询大多按 userId 隔离；并非所有接口都存在越权。
- 商业钱包具有行锁、预留、唯一账本事件和重复结算检查；支付成功与发放额度使用事务，值得保留。
- 主分析任务已拆分 checkpoint，KIE 通用聊天调用已集中，主上传已使用 R2 直传；这些改造无需推倒重写。
- 扫描 app/lib/workers/scripts/package.json，未发现仍运行的 Vercel Blob、B2 或 OpenRouter 调用；数据库有 OpenRouter 历史枚举。是否删除历史枚举应依据旧数据迁移，不属于紧急修复。
- 已删除的悬浮助手不属于当前创作 Agent；当前 Agent 的问题是 A02/A05/A12。

## 可暂缓，不自动纳入本轮修复

- 队列吞吐扩容：当前定时器每轮只推进一个任务步骤，结束后等待 60 秒。需要先测量目标并发；不能把用户关闭浏览器后的缓慢进度说成完全不执行。排队过期的正确性归 A07，容量提升可另行安排。
- 大规模拆分服务、引入新的消息中间件、重写整个 model registry、目录重组，不是解决上述问题的前置条件。
- 旧依赖和历史枚举继续清理，应先证明没有调用和数据依赖；不为了减少文件数增加迁移风险。

## 建议讨论的实施批次

1. 入口与权限：A01-A04。优先恢复上传衔接，禁止未经授权的平台 Key 使用和跨用户资源读取。
2. 执行与一致性：A05-A08、A11。共享执行规则，补终态与 Worker 契约，修复重试/恢复竞争。
3. 商业闭环：A10、A13。先确认产品的钱包和付费范围，再统一授权及退款核对。
4. 资源与真实输出：A09、A12、A14。清理生产演示回退，统一媒体限制及保留策略。
