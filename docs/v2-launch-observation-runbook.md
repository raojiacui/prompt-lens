## 建议的发布后观察顺序

这是人工执行建议，不是已启动的定时监控，不产生新的监控订阅。

1. **正式 Web 切换后立即**：记录域名对应的部署 ID 和 Git SHA，确认 Google/GitHub、邮箱验证码、旧会话及工作台访问。实际验证码邮件测试随正常验收执行，本次没有发邮件。
2. **恢复 Worker 调度时**：按 ADR 0037/0046 恢复正式回调，核对真实鉴权及返回结果。启动后约 1 秒可能开始扫描，已有测试订单、复核及清理候选会进入现有规则，不能当作空机器操作。
3. **首批业务验收期间**：保留正常任务 ID，用少量经授权的正式素材和调用分别验证上传/链接、两次试用、分析、改写、生成；观察关闭浏览器后仍能推进。模型实测按负责人决定放在上线后，具体请求仍按验收范围执行。
4. **任务结束后**：确认结果能打开、分镜画面可读、额度单次结算、未知结果仍待复核；结合连续三轮成功的无工作扫描与本地无媒体处理验证挂起，再验证新任务唤醒。不能仅看到 suspended 就判定挂起机制通过。
5. **建议首小时有人观察**：完成一次正常任务、检查 Web/Fly 错误和 Gmail 到达；确认基本流程前不扩大推广。首小时长度是观察建议，不是后台超时阈值。
6. **下一轮每日 Cron 后复查**：核对部署中的三个 Cron 定义、实际执行记录、七天内容清理及受保护样例；同时核对测试订单/复核状态。仅有 HTTP 200、机器空闲或无错误日志都不足以证明所有子任务完成。
7. **另行收尾**：支付宝资料提交、审核与额度、真实支付/退款验收按第 009 项；不能因为页面已上线就标记正式收款通过。

## 如何判断异常

以下为人工排查提示，不会自动判任务失败、扣款或触发回退。

| 观察到的现象 | 解释及下一步 |
| --- | --- |
| “登录校验失败”或状态同步中断 | 页面可能在显示旧快照。先恢复同一账号登录，再看同一任务；无需重新提交分析 |
| 后台超过 2 分钟无新检查点 | 这是页面已有提示；素材/模型仍可能在运行。结合逐镜头阶段、最近同步和错误码核对，不能等同超时失败 |
| Worker 连续 3 轮 commercial.reconciliation.failed | 建议开始人工排查。轮次间隔受每轮请求耗时影响，单轮请求超时为 290 秒，不能把 3 轮当作固定 3 分钟 |
| 回调 401 或 404 | 优先查两端 Cron 配对、正式域名及 V2 来源；这两类错误可直接排查，无需等满 3 轮 |
| 任务有进展但页面未更新 | 核对会话、网络及同一任务的最近同步；页面错误不等于后台没有执行 |
| HTTP 200 但任务/邮件不推进 | analysis-dispatch 的 recoveryErrors、业务 review 状态、通知错误以及子任务日志仍需检查。commercial-reconciliation 的 checked 只计已调用查单过程，不能证明每笔订单已结清 |
| 无任务且机器 suspended | 按需运行下可能正常；从机器管理列表及已有日志确认，不为保持“在线”反复唤醒 |
| 扫描持续失败、机器未挂起 | 当前失败会重置空闲计数；先处理回调错误，不能因为未挂起就判断还有有效任务 |
| 付费请求响应断开或结果未知 | 保留同一任务及预留，核查已保存结果和供应商状态；未经确认不再次生成、不重复扣费 |

## 对照日志事件

| 日志事件 | 位置及用途 |
| --- | --- |
| commercial.reconciliation.wake_failed / wake_skipped | Vercel；检查 Web 是否能唤醒正确 Worker、变量是否齐全 |
| commercial.reconciliation.succeeded / failed | Fly；检查回调状态、workRemaining、idlePasses 和连续失败 |
| commercial.reconciliation.suspend_failed | Fly；检查自动挂起请求错误 |
| analysis.dispatch_cron.completed | Vercel；检查 accepted 与 recoveryErrors，不只看路由状态码 |
| commercial.review.escalated / alert_failed | Vercel；检查人工复核升级及业务邮件失败 |
| Alipay reconciliation failed | Vercel；按脱敏 code 定位查单或结算不确定，保留订单状态证据 |

Worker 健康快照中的 lastSuccessAt、lastStatus、consecutiveFailures 等可辅助判断，但本轮不访问运行时端点。所有日志缺失都应结合调用是否发生、部署过滤及平台保留范围判断；不把“没搜到”直接视为“没出错”。

## 发生问题时的处理顺序

1. 保存最小证据：时间及 Asia/Shanghai 时区、正式部署 ID/SHA、任务 ID/请求 ID、路由与错误码、对应阶段。不要把密钥、签名参数、完整支付报文或用户素材复制进公开工单。
2. 区分页面同步、认证、媒体存储、模型服务、调度和结算问题。恢复同一任务状态优先；对已有交付先保存并核对，不主动新建重复收费任务。
3. 若发现重复扣款、越权访问、批量错误清理或全站持续不可用，立即请负责人决定停止受影响操作/回退；处理时考虑 Web 派发、Vercel Cron 和 Fly 回调的全部入口。本文不授予助手自行停服、退款、清库或回退权限。
4. 按 ADR 0032 确认旧部署 dpl_AhKmkGrgiKoL25A8KfS8jcLGcBAV 仍存在且可选，再由负责人明确执行回退。正式项目、域名和旧 SHA 75eb611f8759745ec743818bce24350691d6ab8d 必须核对。
5. [Vercel 官方回退规则](https://vercel.com/docs/instant-rollback)说明：Hobby 只能快速回退到紧邻的上一个正式部署；回退使用旧构建及其环境，并恢复对应 Cron 定义，项目 Disable Cron Jobs 设置则会保留。最终发布前确认实际套餐及可选目标，首次验收期间避免无必要的重复正式发布挤掉直接回退位置。
6. 回退 Web 不会回退数据库、R2、Fly 或外部模型/支付请求，也不能中止所有已在执行的请求。按实际范围协调后台入口；不恢复旧数据库来覆盖 V2 上线后新增交易。
7. 修复后按本地验证→提交→推送 GitHub→Git 集成重新发布的约定推进；若回退改变了自动生产域名分配或保护状态，恢复发布前另行检查。不以直接上传或手动提升新 V2 代码绕过流程。
