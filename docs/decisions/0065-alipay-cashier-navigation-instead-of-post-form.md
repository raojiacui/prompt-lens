# ADR 0065：以付款地址跳转替代自动提交表单，避免收银台空白

- 日期：2026-11-13。
- 状态：本地修复、49 项针对性测试、13 项浏览器回归及类型检查通过；尚未推送或发布，正式支付验收仍待完成。
- 关联：ADR 0039、0064；上线记录第 028、029 项。

## 背景与证据

负责人在正式站体验包付款弹窗看到持续加载付款码，打开同一订单的备用付款页也为空白。浏览器只读观察确认两处都停留在本站 `/api/payments/orders/.../pay`，尚未完成支付宝收银台跳转；正式最近 15 分钟 error/fatal 查询没有返回日志，不能据此判定支付宝额度或真实交易已通过。

现有实现由支付宝 SDK 生成自动提交的 POST 表单，付款路由的 CSP `form-action` 只允许两个网关地址。Chromium 对表单后续重定向继续检查该限制。隔离复现表明，网关转往不同收银台来源时会被拦截并留下空白页面。此为已复现的代码缺陷；尚未获得用户原浏览器的完整控制台记录，正式问题必须在发布后以同类流程复验，不将本地模拟视为真实支付宝验收。原弹窗也没有加载超时说明。

## 决策

- 使用已安装支付宝 SDK 明确支持的 `pageExec(..., "GET", ...)` 生成签名付款地址，经现有鉴权及订单状态守卫后以 303 导航。内嵌与独立付款入口复用同一订单，不新建支付宝订单或换接口产品。
- 返回前严格限制签名地址为正式或沙箱 SDK 网关的精确 HTTPS origin/path，拒绝任意外站、仿冒域名、其他路径、用户信息和 fragment。不扩大 CSP 到任意第三方来源；移除已无用途的自动提交脚本及表单策略，保留同源嵌入、禁止缓存及不发送 Referrer。
- 保留金额、15 分钟绝对截止时间、notify_url、内嵌 `qr_pay_mode=4` 和二维码宽度。独立入口继续携带付款回跳地址，内嵌不跳转父页面。支付成功仍以现有可信通知/查询及事务入账为准。
- 内嵌收银台超过 12 秒尚未加载时显示较慢提示，引导打开同一订单的备用入口；不自动重新下单、不重置有效期、不把加载或超时当作支付成功/失败。
- 删除不用的 `createAlipayPaymentForm`，统一改为付款地址接口。本次仅本地修改、测试及提交，等待负责人单独确认 Git 推送；前次“推送吧”对应的发布已经完成，不沿用为本次新增修复的发布授权。

## 备选方案与影响

- 在原 CSP 中放行更多支付宝子域：仍依赖自动表单脚本及重定向域名清单，且扩大来源，采用 SDK 地址导航避免这项约束。
- 直接放开全部 `form-action`、移除鉴权或改成当面付：扩大安全与产品范围，不采用。
- 仅让用户换浏览器或重复下单：不能解决已复现的表单问题，并可能造成重复支付，不采用。
- GET 付款地址包含签名交易参数，因此继续禁止缓存及 Referrer，不将 Location、签名或完整付款地址写入日志、文档或截图材料。

## 验证计划与边界

针对性回归验证 SDK 参数、金额/截止时间、URL 允许范围、鉴权和订单终态守卫、原有查询及验签。浏览器以全本地网关/收银台重定向复现旧表单拦截并验证新导航，再检查中英文加载超时、原订单复用及已有结算展示。真实扫码付款、异步通知、权益发放及审核额度仍需负责人按授权操作，不伪造订单成功或填写商业验收标记。

## 本地验证结果

- Node 24.13.0 下 6 个相关测试文件共 49 项通过，涵盖精确网关 URL 校验、金额/有效期、同一订单 303、账号归属、终态/过期/取消守卫、查询和响应验签。
- 隔离浏览器共 13 项通过：两个本地 HTTP 来源复现原 POST 被 CSP 拦截且收银台零请求，303 导航则经过同一模拟网关抵达模拟收银台；中英文加载超过 12 秒后显示备用入口，保持同一订单且创建次数仍为 1。既有中英文桌面/手机支付界面及到账轮询、弱网恢复回归通过。
- 浏览器服务使用单独 4107 端口及不可用的隔离数据库地址，未停止已有本地服务；测试中的统计写入被隔离地址拒绝，不涉及正式数据库。临时测试配置、日志及图片不纳入提交。
- 验证只覆盖代码与隔离交互。正式商户的审核、额度、二维码实际返回、真实付款、异步通知及权益到账仍未验证，不将本次回归当作正式收款通过。
