# ADR 0039：区分支付宝技术配置与商户开通/解限证据

- 日期：2026-11-08
- 状态：技术预检完成；2026-11-09 账户核查完成、正式收款 UID 已补齐；额度受限且材料未提交，支付上线准备未标记通过。
- 关联：ADR 0033、0037、0038；上线记录第 009 项。

## 背景

负责人要求继续检查支付宝正式收款、回调及限额解除材料。本项只读核对项目与公开官方说明，不创建订单、付款、关闭交易、退款、提交签约或变更商户资料。历史文件记录过单笔 50 元、单日 1000 元，但没有本轮账户页面证据，不能沿用为当前额度。

## 决策

- 保留正式支付宝 APPID、密钥及网关，不重复读取或处理生产私钥。沿用本日已完成的只读交易查询验签证据，不把“查询不存在订单并验签成功”扩展为商户开通或真实收款验收。
- 收款状态、额度和具体补充材料以负责人账户在[商家平台](https://b.alipay.com/page/portal/home)的当前产品页面为准；官方通用文章或其他产品的额度不能代替账户证据。没有重新申请签约或套用新的开通流程。
- 当前定价和购买权限以源码为准，不沿用旧文档价格，不提高或拆分订单规避限额，也不为测试改成 1 分钱商品。
- 正式 `ALIPAY_SELLER_ID` 缺失，通知源码仅在配置该值时校验 seller_id。官方异步通知说明要求核对接收方，故将取得并核对实际收款 UID、补齐该变量列为发布前待办，不把 APPID 或未知账号当作 UID。
- 当前正式 Web 仍为旧版，通知路由未部署。V2 新通知必须随正式部署验证，不能通过先改正式路由、伪造通知、关闭验签或操作既有订单来制造通过记录。
- 先整理可核实的经营说明和材料差异，具体资质清单待当前平台提示后细化；内容见[支付宝准备单](../alipay-launch-materials.md)。

## 已核对的技术事实

| 项目 | 当前结果 |
| --- | --- |

| 沙箱 | `ALIPAY_SANDBOX=false` |
| APPID / 应用私钥 / 支付宝公钥 | 正式 Production 名称均存在；本轮未回读私钥 |
| notify_url | `https://prompt-lens.cc.cd/api/payments/webhooks/alipay` |
| return_url | V2 源码生成正式站 `/billing/payment/return?orderId=...`，嵌入式支付保留既有专用行为 |
| 签名验证 | 本日 20:27（Asia/Shanghai）既有复验中，正式与测试查询均通过验签并返回 `40004 / ACQ.TRADE_NOT_EXIST` |
| 收款方校验 | 正式 `ALIPAY_SELLER_ID` 未配置，待补；不能仅以签名通过替代接收方校验 |
| 商品 | ¥21.90 体验包可购买；¥63.90 创作包与 ¥139.00 大容量包的 checkoutEnabled 均为 false |
| 商业验收标记 | 正式未设置 `COMMERCIAL_PAYMENT_ACCEPTANCE`、`COMMERCIAL_MODEL_ACCEPTANCE`，本轮保持未设置；标记存在也不能替代证据 |

- 前端购买按钮、下单 API 和支付服务都读取套餐可售状态，高价待开放套餐在服务端也会拒绝，不只依赖按钮禁用。
- 通知源码先验签，再校验订单、金额和 APPID；接收方校验依赖待补环境变量。成功发放通过数据库事务和订单状态保护，重复通知不重复发放。实际生产收款仍需真实通知及补偿查询证据。
- 仅 HEAD/OPTIONS 检查通知地址：当前正式均为 404，与旧正式 Git 提交不含支付路由一致；V2 测试 HEAD 为 405，OPTIONS 为 204、Allow=OPTIONS,POST。路由存在不代表已验证签名或到账，没有发送 POST。
- 为查找可核对的商户 UID，仅只读聚合两库已支付支付宝记录中的 seller_id/sellerId 字段，没有返回可用值；不读取买家账号、证件、完整订单或支付令牌，后续需负责人提供商户 UID。
- 官方通用资料提及在商家后台签约管理中补齐资质，并强调实际审核规则。该页面覆盖多种产品，不能将其中额度或门店材料直接套给本应用。
- 源码已有客服及退款工单说明，但未找到独立用户协议/隐私政策路由。若当前审核要求相应公开页面，需补充确认；本轮不声称存在或自动生成法律条款。

## 验证与待办

- 8 个相关本地测试文件、54 项通过，覆盖金额、同步响应验签、下单权限/停售、订单快照、支付页安全和退款接口边界；SDK/业务依赖为 mock，不代表真实付款或退款。
- 已向负责人索取当前产品状态、限额、补材料原文及商户 UID，尚未取得，不标记本项全部通过。
- 未改代码、价格、套餐开关、环境变量、商户资料、数据库记录、Worker 或部署；未创建/关闭订单，未支付、退款或发送消息给商户/平台。
- 真实付款、回调到账、幂等、异常恢复和批准退款留待正式部署后单独授权验证；正式调度恢复沿用第 007 项顺序，不能提前处理现有队列。
- 临时 HTTP 检查及测试日志保存在忽略的 `temp/`；本项仅本地提交准备记录，不额外推送 V2 触发部署。

## 2026-11-09 更新：依据实际账户页面收尾准备

### 背景与决策更新

负责人授权助手打开支付宝页面并在登录后查找信息。通过产品选择核实 Vibe Pay 的网页应用及原正式 APPID，产品开通页面显示已开通、长期有效，同时明确单笔/单日收款额度均为 0。以当前受限状态安排材料准备，不沿用历史限额、不将签约完成视为可收款。

补全信息页要求上传已上线网站信息，提升至个人长期收款额度：网址不超过 40 字符，经营及支付截图包含完整域名下的首页、商品/服务页、支付页，禁止跳转至其他网站，支持电脑/手机端。页面标注审核周期为 1 个工作日，但未显示批准后具体额度，不承诺审核结果或恢复时间。

账号中心的商户号与收单账号一致。延续此前“缺什么补什么”的环境配置授权，将核对后的 UID 仅补入正式 Production 的 ALIPAY_SELLER_ID，保留应用密钥和 APPID，不修改测试项目。替代方案是继续留空并依赖条件式跳过接收方校验；这会保留既有校验缺口，故不采用。完整 UID 不写入仓库。

### 结果、边界与后续验证

- 新增变量为 encrypted、仅 production，回读实际值匹配；正式环境变量从 54 项到 55 项。变量仍须随下一次正式部署采用，不能据此声称运行中的旧部署已加载或通知已验收。
- 修改前核实根项目绑定仍为测试项目，并通过明确的正式项目 ID/名称限定操作；正式域名仍指向 dpl_AhKmkGrgiKoL25A8KfS8jcLGcBAV，没有触发部署或分支切换。
- 未填写材料或提交审核，未签约、创建订单、付款、退款，未修改商户资料、密钥、价格、套餐或验收标记。
- 待准备与实际正式版本一致的网站及截图，由负责人核对并提交；审核后保存额度及生效证据。需测试访问方式时单独确认，不共享所有者凭据。真实收款仍按原部署后验收顺序进行。
- 本次属于账户事实核查及单项运行配置补缺，无业务代码改动；以平台页面、变量回读和正式域名指向验证，不新增镜像实现的测试。

## 2026-11-09 顺序确认：先部署正式页面，再提交网站材料

- 背景：平台要求已上线的网站和完整域名下的首页、服务/商品及支付页截图；旧正式站与 V2 页面存在差异，提前用测试截图提交不能准确对应待审核的网站。负责人明确要求此项安排在上线后。
- 决策：发布前完成技术配置及可执行预检；其他技术条件具备、负责人批准发布后部署 V2，再采集实际正式页面并提交材料，随后确认审核及生效额度，最后按授权完成真实支付/退款验收。材料审核不再作为 V2 Web 部署的先决条件。
- 替代方案：先用旧版页面或测试站截图申请，或等待新页面审核完成才部署；前者存在版本不符，后者与已上线网站要求形成顺序冲突，均不采用。
- 后果：正式页面部署与正式收款验收分阶段完成，期间额度受限及支付未验收继续明确记录，不承诺发布即具备收款能力，不提前填写验收标记。其他发布条件仍需核查，不通过关闭功能制造验收通过。
- 验证计划：核对正式部署来源及域名、新版页面和通知路由；材料由负责人核对后提交，保留审核及额度结果；取得付款授权并在额度允许后验证通知、权益幂等、恢复及退款。此次仅更新文档，不执行部署、材料提交、付款或套餐开关调整。
