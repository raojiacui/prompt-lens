# 0016：V2 逐镜头准备与即时结果交付

- 日期：2026-10-29
- 状态：实现及本地回归完成，发布状态以 Git 提交对应的 Vercel 部署记录为准。
- 范围：V2 自动拆镜后的分析；用户明确要求先优化素材准备和结果保存，并发仍为 2。

## 背景与证据

任务 4bd3aa12 的确认记录为北京时间 17:34:36，镜头任务直到 17:47:58 才创建，首个模型调用约 36 秒。11 个镜头模型调用平均约 36 秒，7 个结果由过期恢复提交，检查点到正式保存最大约 107 秒。旧 runtime 日志已超过 Hobby 保留期，无法确认历史中断由连接、锁、调用生命周期还是其他因素造成。

旧流程一次性准备所有片段、关键帧和音频，直到整批返回才创建镜头任务；分析启动不复用用户预览时已经生成的素材。用户要求准备好一个就送分析，并与下个镜头素材准备重叠。

## 决策

1. 新自动拆镜报价保存 executionMode=scene_pipeline_v1。确认后立即创建版本、镜头占位和独立任务，不等待整批素材。每个镜头任务自行准备一个镜头，再调用其快照中的模型及 Key，完成后立即保存并补位。
2. 同一个视频最多两个运行任务，包含准备和模型阶段；供应商总占位限制不变。一个任务等待模型时，另一个可以准备素材。本次不提高并发，不修改 Worker 拆镜算法或阈值。
3. 优先复用同一用户、项目、媒体地址、sourceHash 和精确起止时间对应的预览缓存。片段和三张关键帧必须属于同一个准备 ID / 镜头 ID，不能拼接不同镜头。未命中时仅请求该镜头的 assets，沿用 Worker 的 sourceHash 校验。素材就绪以事务保存到项目镜头及父任务，后续手动重试复用已准备内容。
4. 新流水线单镜头素材请求最多 60 秒；模型重试共享该调用剩余预算，模型/准备总体为 270 秒目标，给 300 秒函数预留保存和调度时间。素材失败不调用模型，其他镜头继续。整段不拆镜的任务仍走原流程。
5. 原有已创建任务保持原 executionMode。历史批处理和恢复检查点仍兼容；紧急回退可在新报价使用 ANALYSIS_SCENE_PREPARATION_MODE=batch，不改写已经确认的任务。
6. 模型返回后仍先持久化答案，再执行有 fencing 和事务锁的正式保存。状态查询发现已持久化但未提交的答案时立即提交，跳过旧的 20 秒过期等待，并在同次响应中返回最新 bundle。交付提交使用 skip locked，不阻塞正在写入的执行器。所有路径只保存既有答案，不再次推理；正常和并发交付均幂等。
7. 内部调度完整消费小型确认响应，替换主动取消响应体，避免对拥有 after 工作的请求主动发出断开信号。这是调用生命周期方面的保护，并非已证实的历史故障唯一根因。记录 deliveryFlush、preparationMs、modelMs、保存阶段和缓存命中，区分正常交付与过期恢复。
8. 页面继续每约 4 秒查询，已完成镜头可在任务运行期间展示，不要求整条完成。交易结算仍按成功镜头且只执行一次。若新流水线仅部分素材准备成功，成功分析按原价结算，未完整交付的拆镜费释放；手动补试成功后按累计结果结算差额，不重复分析或扣费已成功镜头。

## 验证与边界

- 172 项组合回归通过，1 项既有原生 PostgreSQL 专用测试跳过。覆盖首镜头模型运行期间第二镜头准备、首结果不等后续素材、两个运行位置上限、缓存源哈希/边界隔离、即时交付竞态、素材失败及补试、结果只保存一份、余额和模型调用幂等、原批处理兼容以及模型重试预算。
- 本地无头浏览器用模拟接口验证首个提示词在任务运行时显示、后续镜头稍后补充；既有拆镜缓存/报价过期回归保持通过。
- TypeScript 检查和生产构建通过后才发布。没有重跑真实用户任务或调用真实付费模型；真实首结果延迟和恢复比例需要下一条任务的分阶段指标对比，不能承诺固定耗时。
- Worker API 无需变更或重启，无数据库迁移；没有复制主站代码到 V2，也不发布 main。
- 命中预览缓存时不调用 Worker；未命中时各镜头调用既有单镜头 API，因此仍会分别读取源文件。本轮未实现 Worker 源文件驻留缓存，先消除整批素材就绪屏障，后续可独立减少这部分媒体 I/O。
