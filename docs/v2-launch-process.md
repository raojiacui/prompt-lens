### 已确认顺序

1. 先逐项确认环境变量、数据库、存储、Worker、登录、支付回调等准备事项，并完成相应验证。
2. 提前准备与此分支路线匹配的构建保护规则；完成 V2 验收、版本记录、备份及回退方案。当前仅记录要求，不执行修改。
3. 前置条件全部满足后，进入正式发布窗口。**正式项目切换跟踪分支并触发部署，放在上线准备完成后的最后一个发布切换步骤。**GitHub 默认分支调整安排在同一窗口，分别核对。
4. 正式部署使用已验证、已提交并推送到 GitHub 的确定版本，通过 Git 集成发布；不以 CLI 上传或手动提升代替约定流程。
5. 部署后立即核对正式项目、部署来源、Git SHA、正式域名指向及真实业务流程。最终切换之后仍需正式站验收。
6. 正式站验收后，再讨论测试项目后续用途；当前不删除测试项目、数据库、存储或样例资源。

## 002：保存旧正式版本与部署回退基线

- 确认及执行日期：2026-11-08。
- 状态：归档已执行并验证；实际回退未执行。
- 授权范围：负责人明确授权补充记录，并准备、发布当前旧正式版本的回退归档，要求不影响现有线上站。
- 决策记录：[ADR 0032](decisions/0032-pre-v2-live-rollback-release.md)。

### 已确认方案

1. 给当前正式站实际运行的旧提交创建固定备份标签及 GitHub Release；`main` 与 V2 继续分开，不合并、不移动现有分支。
2. 未来需要回退时，优先恢复 Vercel 保留的旧正式部署；GitHub Release 保存对应源码，用于追溯及必要时重新构建。真正执行回退需另行明确指令。
3. 按负责人确认，当前旧正式站未使用 Worker，本项不准备旧 Worker 回退包，也不操作任何 Worker。
4. V2 环境变量增加时，仍需保留旧版依赖变量的正确值。本项不导出或公开运行时变量，不修改密钥、数据库或存储。
5. 本项只完成版本归档及部署对应记录，不把它视为数据库备份、全部配置兼容或正式上线验收已通过。
